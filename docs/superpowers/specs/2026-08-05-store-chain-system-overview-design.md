# מסמך אפיון-על — מערכת ניהול רשת חנויות (Java, Client-Server)

תאריך: 2026-08-05
סוג: מסמך אפיון-על (Overview) — מטלת קורס פרויקט (מכללת HIT)

## 1. רקע ומטרה

זהו פרויקט גמר קורס במכללה (לא פרויקט מסחרי/פרודקשן). הדרישות המלאות פורטו על-ידי המרצה והועברו כלשונן (ראו סעיף 3). מסמך זה הוא "מטריית-על" שמארגנת את הדרישות ומחלקת אותן לתתי-פרויקטים ניתנים לביצוע בנפרד, כל אחד עם spec ותוכנית עבודה (plan) משלו.

**מסמך זה עצמו אינו שלב ביצוע** — הוא רק ריכוז והבנה של כל הדרישות, כדי שכל שלב עתידי יישאר תואם להן. תתי-הפרויקטים בפועל (החל מ-Entities) יתועדו כל אחד במסמך spec נפרד תחת אותה תיקייה.

## 2. אילוץ מחייב על פני כל השלבים — רמת קוד

> **זהו האילוץ הכי חשוב במסמך, וחל על כל שלב עתידי ללא יוצא מן הכלל.**

- הפרויקט מוגש כמטלת קורס אקדמית (מכללה), והסטודנט צריך להיות מסוגל **להסביר כל שורת קוד** בעל-פה.
- יש להימנע לחלוטין מקוד "מרשים" אך לא מוסבר: תבניות עיצוב (Design Patterns) יהיו רק אלו שנלמדות/נדרשות במפורש (למשל תבנית לניהול תור בצ'אט), ותמיד הגרסה הכי פשוטה וה"ספרותית" (textbook) שלהן — לא גרסה מתוחכמת/מוכללת.
- אין להוסיף שכבות הפשטה, ספריות חיצוניות לא-סטנדרטיות, frameworks כבדים (Spring וכו') או "generics מתקדמים" שלא נדרשים במפורש. Java רגיל + Maven + JUnit + Swing (לפי הצורך) מספיקים.
- אין להוסיף פיצ'רים / ולידציות / edge-cases שלא נדרשו — פשטות עדיפה על "עמידות" יתרה שלא ביקשו.
- כשיש בחירה בין שתי דרכי מימוש, יש להעדיף תמיד את הדרך שסטודנט ממוצע בקורס ידע להסביר ולשחזר, גם אם היא "פחות אלגנטית".
- אין לחשוף שימוש חריג/בולט ב-AI (למשל: תיעוד גנרי-מדי, מבנה קוד לא-אנושי, פיצ'רים "יפים" שלא נתבקשו).

## 3. הדרישות המקוריות (כלשונן מהמרצה)

### 3.1 ניהול משתמשים (Authentication)
- מסך חיבור ואימות משתמשים.
- מסך אדמין להגדרת חשבונות (פרטים ומדיניות סיסמאות).
- מניעת התחברות כפולה של אותו משתמש ממספר מחשבים בו-זמנית.
- תצוגת ממשק מותאמת תפקיד (מנהל משמרת, קופאי, מוכר) וסניף.

### 3.2 ניהול לקוחות ומלאי (מיקוד OOP)
- מלאי חנות נפרד שמתעדכן בזמן אמת אצל כל עובדי הסניף.
- ממשק קנייה ומכירה המציג את המלאי הקיים.
- ניהול לקוחות: שם מלא, ת.ז, טלפון וסוג לקוח (חדש, חוזר, VIP).
- **דגש ארכיטקטוני חובה:** מחלקה נפרדת לכל סוג לקוח. כל מחלקה מטפלת במבצע ובמסלול רכישה שונה — פולימורפיזם בפעולת הרכישה.

### 3.3 מערכת תקשורת וצ'אט (Concurrency & Design Patterns)
- צ'אט אחד-על-אחד בין עובדים מסניפים שונים.
- אפשרות למנהל משמרת להצטרף לצ'אט קיים.
- ניהול תור לחיפוש עובד פנוי.
- שימוש ב-Design Pattern (מתוך לימוד עצמי) לניהול התורים וקבלת השיחות.
- מנגנון התראות "אופליין": שמירת בקשות שיחה בצד שרת אם אין עובד פנוי, והקפצת התראה כשהמשתמש מתפנה.

### 3.4 דוחות ולוגים
- לוגים מקיפים: עובדים, לקוחות, קניות/מכירות, פרטי שיחות (כולל אופציה לשמירת תוכן השיחה).
- הפקת דוחות סטטיסטיים לפי סניף, מוצר או קטגוריה.
- ייצוא דוחות ל-JSON (חובת לימוד עצמי) + אפשרות הצגה במסמך Word.

## 4. פירוק לתתי-פרויקטים (Milestones)

הפירוק הבא תואם את תוכנית העבודה שהמרצה עצמו הציע, כל שלב הוא תת-פרויקט עצמאי עם spec + plan משלו:

| # | שלב | תוכן | תלוי ב- |
|---|------|------|---------|
| 1 | **Entities / מודלים** | Employee, Branch, Product, Inventory, היררכיית Customer (New/Returning/VIP) עם פולימורפיזם ברכישה | — |
| 2 | **Server** | Sockets, ניהול Threads מול ריבוי לקוחות, מניעת התחברות כפולה | שלב 1 |
| 3 | **Client GUI** | מסכי Swing: התחברות, אדמין, מסך עובד לפי תפקיד/סניף | שלבים 1-2 |
| 4 | **Concurrency מתקדם — צ'אט** | תור לעובדים פנויים (Design Pattern), הצטרפות מנהל משמרת, התראות אופליין | שלבים 1-2 |
| 5 | **דוחות ו-I/O** | ייצוא JSON, מסמך Word, לוגים | שלבים 1-4 |

**שים לב:** שלב 1 מתחיל כעת. שלבים 2-5 ייפתחו כל אחד ב-spec נפרד כשמגיע תורם, כדי לא לתכנן פרטים לפני שיש החלטות בפועל משלב 1.

## 5. כלים ומבנה פרויקט (חל על כל השלבים)

- **Build tool:** Maven (`pom.xml`), מבנה תיקיות סטנדרטי `src/main/java` / `src/test/java`.
- **IDE:** IntelliJ IDEA.
- **בדיקות:** JUnit (unit tests לכל מחלקת לוגיקה לפני כל בדיקה חיצונית/הגשה — נדרש במפורש במסמך המקורי).
- **GUI (שלב 3):** Swing (Java סטנדרטי, ללא JavaFX/ספריות UI חיצוניות).
- **תקשורת (שלב 2):** `java.net.Socket` / `ServerSocket` רגילים, ללא frameworks רשת.
- **דוחות (שלב 5):** JSON — ספרייה פשוטה שנלמדת בקורסים כאלה (כגון Gson או org.json); Word — Apache POI, אך רק אם המרצה דורש בפועל מסמך Word אמיתי (יש לוודא בשלב 5).
