01 — Overview

מה המערכת עושה

רשת חנויות בגדים עם כמה סניפים. עובדים מתחברים מכל מחשב, רואים מידע מותאם לתפקיד ולסניף שלהם, מבצעים רכישות מול מלאי אמיתי, מתקשרים עם עובדים בסניפים אחרים בצ'אט, ומנהלים דוחות ולוגים — הכל דרך שרת Socket יחיד שכל הלקוחות מתחברים אליו.

הפרויקט נבנה כמטלת קורס אקדמית (HIT) — כלומר כל שורת קוד צריכה להיות ניתנת להסבר בעל-פה על-ידי הסטודנט. לכן נמנענו במכוון מתבניות עיצוב, ספריות או הפשטות שלא נדרשו במפורש: אין Framework כמו Spring, אין ORM, אין שכבות מיותרות — Java רגיל, Maven, Sockets סטנדרטיים, ו-Swing רגיל לממשק.

הפיתוח התבצע ב-5 שלבים לפי תוכנית העבודה המקורית של המרצה (Entities → Server → GUI → Concurrency/Chat → Reports/IO), ולאחר מכן עבר סבב סקירה נוסף מול נוסח הדרישות הרשמי המלא, שבו נסגרו כמה פערים אמיתיים (ראו סעיף מיפוי דרישות).

05 — Design Patterns

תבנית עיצוב אחת, שני שימושים

התשובה הנכונה לשאלה "כמה תבניות עיצוב יש בפרויקט" היא אחת — Singleton — שמופיעה פעמיים כי שתי הבעיות זהות במבנה שלהן: "צריך בדיוק מופע אחד, נגיש מכל מקום".

chat.ChatDispatcher

ניהול תור הצ'אט (נדרש במפורש, §9)

מופע יחיד מחזיק את תור ההמתנה ומפת השיחות הפעילות של כל השרת. כל המתודות synchronized — נעילה אחת פשוטה, לא נעילות עדינות מרובות.

private static final ChatDispatcher INSTANCE = new ChatDispatcher();
private ChatDispatcher() {}
public static ChatDispatcher getInstance() { return INSTANCE; }
logging.SystemLogger

לוג המערכת — שימוש חוזר טבעי, לא תבנית שנייה

לוגר הוא הדוגמה הכי קלאסית ל-Singleton בתעשייה. חיווט לכל שירות קיים דרש שורה אחת — getInstance().log(...) — בלי לשנות אף קונסטרוקטור.

AuthService.login(...) {
  ...
  SystemLogger.getInstance().log("EMPLOYEE", "Login: " + username);
}

07 — Known Limitations

מגבלות ידועות, מתועדות בכוונה

כל אחת מהן הייתה החלטת עיצוב מודעת — לא דבר שנשכח. שווה לדעת להסביר למה, לא רק שכן.

אין מסך צ'אט ב-GUI

הצ'אט מוכח במלואו ב-ChatIntegrationTest מול Socket אמיתי. מסך צ'אט אמיתי דורש Thread קורא ברקע בצד לקוח שיודע להבדיל בין "תשובה לבקשה שלי" לבין "הודעה שקפצה אליי" — תשתית שלא נבנתה כי לא נדרשה עדיין הודעת Push בשום מסך אחר.

נתונים בזיכרון בלבד

עובדים, לקוחות, מכירות ושיחות פעילות נשמרים ב-RAM, לא בקובץ/DB. אין persistence בין הרצות שרת. זו נקודת קצה מוכרת של הפרויקט מאז שלב 2.

סיסמאות ללא הצפנה

נשמרות ונבדקות כמחרוזת רגילה. החלטה מודעת לרמת קורס — לא תקלת אבטחה שנשכחה.

מדיניות סיסמאות קבועה בקוד

6 תווים + ספרה, לא ניתנת לעריכה דרך מסך האדמין. המפרט לא נתן ערכים מדויקים, בדיוק כמו אחוזי ההנחה בשלב 1.

רק אירועים מוצלחים נרשמים ללוג

ניסיונות כושלים (סיסמה שגויה, מלאי חסר) לא נרשמים — שמירה על היקף מינימלי, לא דרישת אבטחה שהוזנחה.

לא נבדק ויזואלית בסביבה זו

כל תרחיש נבדק אוטומטית (JUnit) ובאמצעות סקריפטים המדמים בדיוק את פרוטוקול הרשת שה-GUI משתמש בו, כולל הרצה ידנית של השרת והלקוח מקצה לקצה. לא בוצעה לחיצה בפועל על כל כפתור בסביבה גרפית — מומלץ לעבור על כל המסכים ידנית לפני ההגנה.

08 — Defense Prep

נקודות שכדאי לדעת להסביר

השאלות הכי סבירות, ותשובות קצרות שמראות שהבנתם את הבחירות, לא רק העתקתם קוד.

למה Singleton ולא Observer/Strategy לניהול התור?
כי יש בפועל מופע אחד רצוי של מנהל-התור לכל השרת — זו בדיוק הבעיה ש-Singleton נועד לפתור, לא בחירה שרירותית.
איך התור משרת גם "חיפוש עובד פנוי" וגם "בקשות אופליין"?
זה אותו מבנה נתונים בדיוק: מי שלא נמצא לו שותף — נכנס לתור בעצמו. הבקשה "הממתינה" והעובד "המחפש" הם אותו מצב.
איך יודעים שרק מנהל יכול ליצור חשבון/לראות דוח סניפים/לוגים?
בדיקת Role בצד השרת (לא רק הסתרת כפתור בלקוח) — הזהות של המשתמש היא תכונה של החיבור עצמו (ה-Socket), לא טוקן שנשלח מחדש בכל בקשה.
איפה בדיוק רץ הפולימורפיזם של הלקוחות?
Customer.purchase() קוראת ל-calculateDiscount() המופשטת; SaleService בונה את תת-המחלקה הנכונה לפי CustomerType שנשלח מהלקוח, ואז קוראת ל-purchase() בלי לדעת איזו תת-מחלקה זו בפועל.
למה אין בדיקות JUnit למסכי ה-Swing?
בדיקת רכיבי GUI דורשת תשתית נוספת שהיא מעבר לנדרש בקורס. כל הלוגיקה שהמסכים קוראים לה כבר מכוסה ב-JUnit; המסכים עצמם הם "צינור" דק בלבד.
איך מוכיחים שמסמך ה-Word אמיתי, לא רק "קובץ נוצר"?
WordReportExporterTest קורא את ה-.docx בחזרה עם Apache POI ובודק שהכותרת והנתונים בטבלה נכונים — לא רק שגודל הקובץ אינו אפס.
